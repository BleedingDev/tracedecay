The existing Native application port and staged SQLite store provide bounded extension points for the required advisory lifecycle. The adapter already dispatches every operation. The missing work is durable provider-local operations, source/validity inputs, and their recall consumers. Canonical fact mutation is a separate authority and supplies none of these missing implementations.

The completed common profile must negotiate feedback, correction, deletion, inspection, maintenance, snapshot export/restore and replay as required capabilities. Missing-capability refusals remain truthful failure evidence, but do not satisfy compatibility. The descriptor and required-capability handshake must advertise and require the same implemented profile; successful no-ops cannot fill a missing operation.

Existing mechanisms worth preserving:

- `S::stage_or_duplicate` uses an immediate SQLite transaction, derives payload digest from actual stored bytes, and persists receipt/reference/effect digest with the row. The primary key is exact scope plus delivery key; the secondary key is exact scope plus source authority/event/revision/payload digest. `StagedOutcome` at S:311–322 distinguishes committed, duplicate and conflict. Extend this mechanism for lifecycle operations rather than returning `success_reply` for writes.
- `S::recall` checks all five checkout fields in SQL, then re-derives each row's seven-field origin digest, S:807–845. `P::staged_scope_attestation`, 2374, intentionally emits the checkout claim while retaining origin session metadata. The comment at P:1780–1783 still says exact-session recall; executable SQL and T:1508/S:1582 establish the actual cross-session behavior.
- `P::build_native_recall_reply_with_response_bytes`, 1891–2096, already enforces content limits, a shared candidate ceiling, a reserved eligible canonical fact and full serialized response bytes. Its coverage currently uses the returned fact/staged lists as both scanned and matched counts, P:2036–2038 and 2486–2490. A bounded S scan must return its own coverage before temporal filtering/exclusions/replay can report completeness honestly.
- Corruption checks presently verify scope digest, S:841–845. Recall reads stored payload bytes and `payload_sha256` independently at S:847–870; it does not rehash the payload against that column. Restore and recall need this validation, plus applicable source/lineage invariants, to support the required corrupt-state safety assertion.
- `P::NativeReadActor` has one worker and a queue capacity of one, P:1495–1500. `receive_actor_reply`, 1573–1596, polls cancellation/deadline every 10 ms. `Drop`, 1599–1612, joins the worker. Reuse the bounded queue for reads. Do not add effectful commands that can continue committing after the waiting caller returns a generic no-effect cancellation. S operations currently accept no `OperationControl`, and its mutex wait is not bounded by the SQLite busy timeout. New writes need control checks before mutation/commit, durable operation outcome recovery, and an unknown-effect result when commit status cannot be proved. A read timeout alone cannot make blocking SQLite work cancellable.

Migration should stay inside the existing provider database. `S::initialize_schema`, 958–979, currently creates v1 tables in one transaction, writes `PRAGMA user_version=1`, and refuses a newer schema. It has no v1-to-v2 migration. Keep the existing file location and perform an explicit transactional v1 upgrade; opening a new empty filename would silently lose existing advisory memory.

Preserve v1 payloads, exact origin fields, admitted sequences, provider references and all original effect evidence. Add provider metadata/generation, operation outcomes, source revisions/validity/lineage and independent privacy-deletion state within the same SQLite authority. Existing retention tombstones must remain payload-free and continue answering duplicates. They cannot be reclassified as known privacy deletions because v1 stores no reason. Existing `source_revision` values remain legacy envelope revisions unless retained canonical evidence establishes their actual source revision. Missing validity remains unknown; local admission time must not become reconstructed source history.

Migration tests need an actual pre-upgrade v1 database fixture containing live rows, an evicted row and stored duplicate evidence. Reopen with the new implementation, verify byte-identical old identity/evidence and recall under the declared legacy validity policy, then perform feedback/correction/delete and reopen again. Inject failure during migration and prove the transaction rolls back. Opening a schema-ahead database must still fail. A new empty-store test does not cover this migration.

Contract and producer decisions that must precede implementation:

1. Define the canonical source selector, actual source revision, observation ID, validity evidence and operation target. Specify revision-wide versus source-wide deletion and authorized cross-session targeting. The missing consumers are P's source extraction/candidate projection and S's source index/lifecycle queries. The existing `version` extraction and provider reference are insufficient substitutes.
2. Supply host-authorized canonical history, original origin scope, ordering and current deletion history to replay and fresh-namespace restore. The Native v1 store cannot reconstruct evicted text or discover deletions that occurred after an exported snapshot. This is a producer handoff to the history owner, not Native permission to invent history.
3. Set common mutation effects, durable duplicate/source-already-applied accounting, generation semantics and interrupted-commit outcomes. Current `staged_effect_reply` echoes the observation payload, P:865–902; lifecycle responses need their actual common result schema. Avoid reusing `terminal_for_call`'s no-effect success or failure-before-dispatch construction for uncertain writes, P:716–755.
4. Set the accepted common observation kinds and the behavior for legacy records with unknown validity. Current `extract_message_text`, S:1042–1068, reads only `facts.kind == message`. The Native baseline explicitly measures rejection of source-edit/test/feedback-outcome observations and zero admitted context, B:10–16 and 192–293. It proves neither successful common observation support nor lifecycle compatibility.
5. Keep canonical fact history separate. Native currently opens the retained target for read and searches current facts in `recall_project_memory`, P:1688–1775. `verify_current_fact`, P:2600–2685, reads per-fact history only to verify a promotion receipt; it is not an as-of search implementation. Common historical canonical-fact reads need their own retained-authority producer. The Native worker must not project current facts into past answers or route advisory correction/delete/feedback into canonical fact mutation. Shared handling of these fact candidates belongs to the root's interface decision.
