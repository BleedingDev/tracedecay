# Native and NCM comparison protocol

Protocol revision 1, prepared against `6010f31e7` on `feat/pluggable-memory-providers-v2`. This is the input to `pm-comparison-harness` and `pm-measure`. Root reviews and freezes it before the comparative runner or new measurements start. It contains no new measured results. The quality thresholds, timing targets and trial counts below are predeclared; changing them after inspecting results starts a new experiment with fresh held-out cases.

## Run the existing evaluator through the real host

Produce four matched lanes for each of Claude Code and Codex:

| Lane identity | Real execution | Permitted advisory input |
| --- | --- | --- |
| `provider:tracedecay.native` | Production Native adapter, application port, host admission and context assembly | Native provider-local memory; NCM disabled in the primary comparison |
| `provider:ncm` | Production NCM adapter and Rust worker with the pinned real MiniLM encoder, host admission and context assembly | NCM provider-local memory; Native advisory provider disabled |
| `no_memory` | Same daemon, canonical services, tool and task runner | No advisory provider call or advisory content |
| `explicit_documentation` | Same daemon, canonical services, tool and task runner | Only current-revision fixture `docs/**`, `notes/**`, top-level `AGENTS.md`, `README.md` and `CLAUDE.md`, under the same advisory quota |

Canonical facts, current code evidence, session evidence, privacy, scope authority and the canonical portion of each context answer remain enabled and identical in all four lanes. Disabling Native advisory recall must not disable canonical fact access. Record the canonical contribution and its cost separately. Python Biomem is an existing numerical/backend fidelity reference; it is outside the four-lane host comparison and task-benefit aggregate.

Run two core experiments. `corpus_regression` preserves the nine existing scenario inputs. `host_comparison` drives the shipped host paths with positive and negative cases and measures retrieval usefulness, safety, source fidelity, exact context tokens, performance and resources. Optional `task_benefit` executes downstream tasks using the resulting context only under separate authorization for that runner and any paid model use. No paid task-model use is authorized by this protocol. Provider conformance, source admission, retrieval usefulness, optional task outcomes and performance each receive their own verdict. A success in one does not supply evidence for another.

## Input freeze and execution order

1. Root selects one implementation snapshot and the reviewed common conformance profile. Record the source revision, build/features, provider state schemas, encoder/model artifacts, runtime versions, hardware/OS, tokenizer, effective policies and workload schedule once. Use the existing identity mechanism for corpus/config equality; new receipt or lock machinery is unnecessary.
2. Validate all regression inputs with the existing loaders. Pin the complete host transcript projection, CLI requests, source changes, session transitions, canonical starting state, provider-local starting state, requested and effective budgets, exclusions and temporal semantics. Completion means the four lanes consume the same logical trace, including failure/cancellation triggers.
3. Prepare fresh held-out cases by the process below. Freeze truth, retrieval rubric and prohibited sources before viewing provider answers. Freeze downstream task verification too if the optional task-benefit experiment is separately authorized. Complete the regression smoke and evaluator negative controls before opening held-out results.
4. For each paired block, create independent mutable stores and process groups. Materialize identical fixture bytes and logical scope identities; record physical path mapping. Pin model artifacts read-only. Run only one heavy host/model process group at a time, using the checkout's existing build/model artifacts.
5. Start and configure the shipped daemon before writing the session transcript. Force initial project mount, wait for canonical import/projection settlement, then use the existing no-hook quiescence control and native lifecycle hook commands. Do not prepopulate provider state by administrative import while claiming hook ingestion.
6. Deliver observations and lifecycle actions in order. Wait for declared durable settlement, record accepted/rejected/unknown effects, and then issue the same host request. For current/as-of/interval/history requests retain all temporal fields; privacy deletion still excludes revoked sources from history. Unsupported required behavior is incomplete, not a skipped success.
7. Capture raw provider reply metadata, host admission/normalization/selection/hydration, final context, operation timing and resource samples. Produce typed run records, attach evidence-backed annotations, evaluate, and compare matched reports. A missing lane still gets its planned trial row with the exact blocker; it is not silently removed from totals.
8. Run the bounded schedule below. Root reviews raw samples, counts, labels and all verdicts before interpreting quality differences. No provider tuning, additional favorable trials or wider budgets follow result inspection in the same experiment.

Authoritative logical time is the fixture's UTC timeline. Operation deadlines use the runtime's current monotonic/wall-clock control, with the same relative budget in each lane. Do not use the baseline's default absolute deadline in year 2100 as a substitute for elapsed-time enforcement. Record the actual deadline and remaining budget at dispatch separately from the logical evaluation time.

For matched recall and performance blocks, compare canonical output bytes and source attribution at each corresponding step before attributing any delta to advisory memory. If background indexing or session state changes canonical output, flag that block as input drift and retain it as an invalid comparison. Do not subtract or fabricate canonical content to repair the comparison. Downstream task runs start with identical canonical state and tools; subsequent task-driven divergence is an outcome and is logged.

## Held-out cases and labels

All nine checked-in scenarios have been inspected, including the five called `held_out` in the older NCM protocol. They are regression data for this experiment. Preserve that older result as historical evidence; do not reuse its split as an unseen sample.

Prepare exactly 18 fresh cases, two per existing behavioral family: stale change, failed approach, cross-session reuse, project/worktree/branch isolation, contradiction, restart/replay, cancellation, corruption and privacy deletion. Use new synthetic fixture content, facts, distractors, queries and evidence. Mere identifier/word substitutions of the inspected answers are insufficient. Include non-keyword paraphrase queries, a true but irrelevant distractor, a plausible stale claim, and an admissible useful source in the applicable families. Positive preconditions must make forbidden-source challenges discriminating.

A case author who has not inspected new provider answers records the source truth, expected useful facts, allowed origin scope, forbidden source lineage, validity intervals, retrieval acceptance checks and evidence references. A second reviewer checks ambiguity before any provider execution. Candidate labels are assigned after capture against that frozen truth by reviewers blinded to provider ID and score. Disagreements become `Indeterminate` unless adjudicated against the frozen evidence. Keep actual labels and reasons; this protocol creates no scores. If held-out output is used to repair a runner or provider, that case becomes regression data; a new frozen set is required for a new held-out claim.

The common conformance fixtures additionally supply budget/exclusion, as-of/interval/history, provider-local feedback/correction, snapshot, canonical replay, switch/rollback, quarantine and cancellation cases. They are correctness coverage, not extra unseen tasks or extra task-score denominators. Run each against both providers with the same assertions, including positive admission before deletion/corruption and unaffected-source recall afterward. Provider-specific internal snapshot formats remain separate; switching replays canonical history and must retain deletion fences.

Keep two evidence classifications distinct:

| Classification | Values and evidence | Reporting rule |
| --- | --- | --- |
| Source admission and retrieval usefulness | Current and relevant, true but irrelevant, stale, wrong scope, deleted, corrupt, unavailable provenance, unresolved; record exact source/revision/scope and host decision. Use existing `CandidateLabel` values for evidence-backed retrieval annotations. | A retrieval `Useful` label means the delivered candidate supplies a fact required by the frozen query rubric, verified against source truth. Rejected candidates remain in the admission ledger and do not enter admitted-candidate precision. This measures assessed retrieval usefulness, not successful downstream task execution. |

The legacy `CandidateLabel::Useful` documentation says the candidate helped the task. Identify core reports explicitly as host retrieval assessments and document the frozen required-fact evidence behind each `Useful` label. Their inherited rubric-derived `task_outcome` is a retrieval-rubric outcome, never measured agent success. The core `useful_recall_precision` gate evaluates these resolved retrieval labels without requiring a decoder/model run. Keep downstream `task_benefit` explicitly unmeasured unless the optional authorized experiment supplies actual task evidence. `Unverifiable` is a resolved label in the existing enum; missing or ambiguous origin evidence must still make the associated safety check indeterminate, even if a numerical label ratio can be computed.

Only after separate authorization for task-model execution, run optional task benefit with the same pinned agent/model/version, prompt template, tools, maximum calls, output-token cap, seed support and timeout in all lanes. Freeze those task-runner settings before results. Without an authorized executable runner, emit `task_benefit: unmeasured`; core parity and host comparison can still complete. Use an existing task runner; this work does not introduce an agent framework. Record actual test/assertion outputs and structured fact-discovery events. Generated prose saying a task succeeded is insufficient. Curation time is measured human effort; automated execution time cannot be relabeled human curation.

For each optionally executed task, retain resolved success/failure, indeterminate outcome, time to completion, tool calls, required and rediscovered facts, exact input/output usage, and curation seconds. Pair the same task and trial across all four lanes. Claim an agent-outcome improvement only from these paired outcomes with uncertainty. Do not infer causality for an individual candidate merely because the full lane succeeded.

## Frozen quality and control gates

- Useful-recall precision minimum is **0.60** on resolved admitted candidates from positive host retrieval cases, pooled by numerator/denominator using the existing evaluator and the frozen required-fact rubric above. Report labeled, missing and indeterminate counts, unique candidates and total admission events. Every scheduled positive retrieval case needs a rubric outcome and every delivered candidate needs a label or explicit unresolved reason; selecting only favorable labels makes the core report incomplete. Optional downstream task execution is not part of this gate. Report macro results as secondary, without replacing the pooled denominator.
- Harmful/stale admitted recall, scope leakage, corrupt-state recall and deleted-source recall each retain a **zero ceiling** from `coding-memory-metrics.v1.json`. Any ceiling violation or indeterminate applicable safety check fails the safety gate. Report that gate beside aggregate task score, compatibility and performance verdicts.
- A zero-admission lane supplies no isolation/deletion/corruption proof by itself. Require verified committed positive content, an exercised forbidden source or corrupt state, and the expected rejection/absence plus a live unaffected control where applicable. A typed cross-project refusal can establish that refusal; it cannot prove same-checkout positive reuse. Keep no-memory/documentation controls in the report with their genuine not-applicable/indeterminate evidence.
- Track deletion by stable source lineage, observation IDs, payload digests and derived-state evidence after deletion, restart, snapshot restore and canonical replay. A forgotten string disappearing is insufficient. Preserve phase: a valid pre-deletion admission is not a post-deletion violation.
- Keep original provider scores and scales in raw results, with rank and declared scale. Compare delivered facts/content, provenance, host decisions and task outcomes. Cross-provider subtraction of native scores has no defined meaning.
- Negative controls must demonstrate that changed source digests, a wrong-scope admission, a deleted source resurrected by replay, a stale current answer, an ignored cancellation and a zero-admission evaluator each fail the appropriate check. Exercise these on development fixtures, not by changing a frozen held-out trial. Missing labels/timings and a mismatched shared-input report must remain visible or be rejected. A HashEncoder substitution must fail the real-model lane identity check.

## Timing and resource record

Keep one append-only measurement row per planned attempt in the comparison report's measurement section. This extends existing `BaselineTimings` reporting rather than creating another scorer. Include trial/block ID, lane/host, case/request/operation ID, state/query population, phase, process group, requested/effective budget, warm-up flag, start/end monotonic time, terminal, provider-contacted flag, durable effect boundary, and measurement status/reason.

Measure these boundaries directly:

- Cold startup: process spawn to daemon/provider/model ready for work; separate config/build/model installation and fixture creation from startup. Record process-cold and reopened-disk state explicitly. Do not call a fresh process filesystem-cache-cold, purge OS caches, or include model download as model open.
- First recall: first text request after readiness to returned terminal, with readiness/model/namespace initialization state recorded. Capture total spawn-to-first-delivered-context as well; do not add unrelated medians to estimate it.
- Warm recall: input dispatch to provider result and, separately, host request start to final context response. Internal spans cover encoding, kernel, IPC/queue, admission, hydration, selection and context packing where instrumentation exists. Missing spans are unmeasured, never inferred by subtracting percentiles. Native has no worker IPC span when none exists.
- Durable observe: accepted host/provider dispatch to persisted acknowledgement; separately hook process start to hook exit, canonical commit to provider settlement and queue waiting. A background journal receipt seen after polling gives a bounded observation interval, not an exact commit instant. Report poll bounds unless the producer emits an exact timestamp.
- Feedback/correction/deletion: request to durable response, plus response-to-first-verifying-read. Correction effectiveness starts at correction submission and ends at first verified corrected recall. Include the polling cadence and right-censor at its deadline.
- Replay/restore: operation start to durable completion and ready recall; shutdown/cancel: signal/submission to terminal, released queue/permits and reaped owned children. Caller return and child exit are different measurements. A success response with a live child is not completed cleanup.

Use the existing macOS collection in the benchmark scripts, including `/usr/bin/time -l` and `ps`, for each owned process group. Record machine model, RAM, OS, power mode, CPU load and build mode. Poll the parent and descendants every 20 ms during measurement; record actual polling gaps and instrumentation CPU cost. Track PIDs with process start identity so PID reuse does not count another process. Never include the operator's daemon or other agents' processes.

For every phase report starting, ending and maximum sampled RSS of host and worker separately, simultaneous process-tree RSS, RSS delta from the same phase's no-memory control, and per-process OS high-water RSS. A sum of separate process high-water marks is not a simultaneous peak. Sampled tree peak is a lower bound if short-lived children can escape polling. ## Failure denominators and uncertainty

The existing evaluator's nearest-rank method remains authoritative: sort completed samples and select rank `ceil(p*n/100)`. Report p50, p95, p99, min, max, median absolute deviation and interquartile range for every phase/population. The current metric catalog supplies p50/p95 recall; p99 and lifecycle/resource distributions are supplemental measurement results, not new quality metrics. With 20 cold samples, p99 is the maximum; disclose the sample size and do not imply a precise tail estimate.

Every table includes `planned`, `attempted`, `provider_contacted`, `completed_success`, `completed_failure`, `deadline`, `cancelled`, `censored`, `unexecuted`, and `warmup` counts. These fields have explicit definitions: deadline/cancelled are terminal classes within completed attempts when a terminal is observed; censored attempts have no observed completion by collection cutoff. Publish their cross-tabulation so they are not accidentally summed twice. Record exact `elapsed_at_cutoff` for censoring. Provider refusal, crash, corrupt state, Busy and timeout attempts remain in planned/task/safety denominators where applicable. They never become missing-at-random samples or zero-time successes.

Show successful-completion latency descriptively, completed-terminal latency including failures separately, and the fraction of all scheduled attempts successfully completed within each target. For deadline/censored success-latency ranks, report bounds: if unknown slow completions could move the requested percentile across the target, that target is indeterminate; if the observed lower bound already exceeds it, it fails. Instrumentation failures keep the semantic outcome, but timing/resource results become unmeasured.

The core retrieval report retains the existing resolved-rubric score and separately reports `case_rubric_passes / scheduled_case_trials` and `query_expectation_passes / scheduled_query_attempts`, with failure and unresolved counts alongside each. These denominators prevent high resolved-only scores from hiding crashes or missing cases. Repeated calls do not create independent quality facts: report unique cases and sources, and use case-level aggregates for comparisons.
