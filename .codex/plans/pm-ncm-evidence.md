# NCM canonical compatibility evidence

Audited the assigned product checkout at baseline `6010f31e7` for `pm-ncm-audit`, graph `pluggable-memory-compat-v1`. This is source evidence, not a runtime validation result. No Cargo/model execution, production changes, operator changes, or plan-status edits were performed. Paths below are relative to this checkout; line numbers identify the audited implementation.

Evidence confidence: field loss, response shape, missing cancellation forwarding, retained provenance columns and superseded-candidate eligibility are directly established by the cited code. The fresh-key revoked-source resurrection and snapshot-ID alias scenarios are source-derived predictions with discriminating tests specified below; they were not reproduced in this lane. Referenced existing tests establish their assertion coverage, not a newly observed passing run.

NCM already has durable learning, source capsules, explicit feedback/correction, privacy rebuilds, snapshots, process supervision, and deterministic kernel recall. Its current adapter does **not** produce a canonical host-admissible recall response. The request translator drops canonical temporal/exclusion/budget semantics; canonical session projection discards evidence needed to reconstruct admissible provenance; the response merely relabels native kernel JSON with the canonical contract ID. Zero-result recall omits the canonical outcome entirely. These are producer/consumer gaps, not reasons to relax host admission or change the model.

## Actual recall wire shape and host rejection

The following is the structural native payload from the derived serde types at K lines 43–101, not a captured model output:

```json
{
  "Candidates": {
    "candidates": [{
      "record_id": 1,
      "source": "opaque namespace-bound source digest",
      "key_text": "retained key",
      "value_text": "retained value",
      "layer": "Stm",
      "activation": 0.5,
      "distance_components": {"cosine_d2": 0.2, "minkowski": null},
      "support_slots": [],
      "validity": "Valid",
      "confidence": {"Uncalibrated": 0.5}
    }],
    "truncated": false,
    "margin_satisfied": true
  }
}
```

Numbers/text/support slots above are illustrative; a real candidate carries its real supporting slots and score. Empty recall becomes `Outcome::Empty` with no wire payload. B `worker_reply`, lines 810–885, maps outcomes to terminal codes and adds effect evidence but does not create a canonical recall envelope. It discards serialization failure with `.ok()` at line 860, another success-without-payload seam to remove.

H `RecallOutcomeV1`, lines 1058–1082, requires provider/instance/registration/readiness/request/scope/generation, `candidates`, `coverage`, `ordering`, `terminal`, warnings. `RecallCandidateV1`, lines 1013–1052, requires canonical identity/content/hash/score/scope/validity/provenance/explanation/reference/sensitivity/class fields. H `admit_recall_reply`, lines 1261–1293, rejects missing payload, decodes with `deny_unknown_fields`, then binds the outcome and admits candidates. Therefore the raw `Candidates` wrapper fails canonical decoding, and empty recall fails `MissingPayload`. Passing existing raw JSON assertions is not host admission.

A `valid_surface_reply`, lines 846–878, intentionally forbids `exact_scope_identity`, public scope components and caller identities inside worker payloads. `invoke` only rebinds the terminal at lines 1295–1308. The correct conversion point must respect this ordering: validate the opaque worker result first, then construct the public canonical outcome in the host-facing adapter with proved origin metadata. Making the worker return public scope objects would collide with the existing containment gate.

Host evidence syntax is separately defined by `recall_provenance_hydration.rs:107–172`: `source:<path>#L…`, `session:<id>#…`, `record:<canonical-id>`. Syntax is only a claim; real authority resolution is mandatory. Neither the NCM opaque source digest nor its numeric `record_id` proves a host canonical record. Do not label an NCM row `record:1` or fabricate transcript ordinals.

## Stable host source versus opaque record identity

1. **Exact namespace is deterministic.** A lines 104–119 hashes profile, project, repository, worktree, branch, agent session and resolved scope digest. A lines 1625–1631 hashes namespace + domain + public source. For canonical session observations, A lines 1690–1714 derives the canonical session forget key from the admitted session relation before hashing. Delete uses the identical hash domain at lines 1643–1655.
2. **Ordinary restart preserves provider mapping.** S `StoredCapsule`, lines 226–252, retains record ID, opaque source, text, embeddings, JSON provenance, status and insertion commit sequence. `insert_capsule`, lines 785–823, allocates the durable counter in the same transaction. O lines 170–190 requires the kernel/store IDs to match. Runtime `engine/runtime/recovery.rs:116–149` rebuilds records from capsules/events and refuses any ID or projection mismatch. The adapter test `tests/rust_backend.rs:702–784` observes canonical content, restarts, recalls it, and deletes by the same host session forget key.
3. **That mapping is one-way and too coarse for host citation.** The session forget key groups a session's source records; the original stable canonical observation ID is checked then discarded. There is no retained inverse map from the digest/record ID to original host source/session/range/revision in the canonical-session path. Existing arbitrary provenance storage cannot recover data the projection never supplied. An in-memory request map would fail after restart.
4. **Privacy rebuild preserves surviving IDs.** P lines 480–544 temporarily rebuilds surviving records, then `remap_record_ids`, lines 569–616, restores old record IDs and advances the next ID beyond all prior capsules. Thus privacy reconstruction itself does not require changing the public identity of surviving records.
5. **Snapshot rollback is a different lineage boundary.** X `build_direct_stage`, lines 935–969, restores the snapshot kernel's own next record ID; `kernel_next_record_id`, lines 1362–1368, reads its old `next_id`. Restore increments epoch at X line 492. A snapshot before record 2, followed by record 2, restore, and a new observation can reuse numeric ID 2 for different content. Feedback/correction currently accept a number with no source/epoch/revision proof. Stable target references must reject this alias even when the caller obtains fresh readiness. This scenario is inferred from source and needs the discriminating test below.
6. **Cross-session reuse needs host authorization.** Changing any exact-scope component changes both namespace and source digest. Existing scope hashing must remain unchanged. Authorized history/replay must convey original origin attribution and deletion decisions through the shared host authority. An NCM-only namespace broadening or copying the current caller's scope onto older evidence cannot solve this.

## Existing lifecycle guarantees and exact residual risks

- **Read-only recall in a loaded healthy namespace:** R lines 138–169 clones an immutable published kernel and calls its read API. K reads records/centers without feedback or time advancement. `tests/engine_transactions.rs:288–308` asserts unchanged commit sequence, state digest and tick across three recalls. It does not prove that opening an existing namespace never writes: R `ensure_handle`, lines 348–359, may resume a pending privacy rebuild. That recovery side effect currently can be triggered by handshake/inspection/recall. Separate readiness/recovery transition from the advisory read if strict read-only lifecycle semantics are required; do not remove privacy recovery fencing.
- **Durable effects:** observation and mutation paths journal idempotent receipts, commit before publication, fence on post-commit uncertainty, and rehandshake after mutation. A invalidates readiness before mutating dispatch at lines 1284–1286 and rejects stale readiness/generation at lines 1213–1225. B lines 820–854 distinguishes committed/duplicate/unknown effects. Preserve these properties.
- **Cancellation:** C `call_cancellable`, lines 180–278, already polls live cancellation; `owner_loop`, lines 612–660, cancels queued work and kills/reaps dispatched work before reuse. B `prove_identity`, lines 260–269, already demonstrates the cancellable client path. Normal invoke/handshake must use it too. The current adapter's post-return token check prevents late success but does not meet prompt cancellation completion.
- **Process lifecycle:** worker owner is lazy and shared (B lines 90–120); `WorkerOptions` defaults at C lines 42–49 enable real encoder, with three restart attempts. Mailbox ceilings are 32 requests / 8 MiB (C lines 19–23). Disabled launch, unexpected exit, backpressure, cancellation and drop have worker tests (`tests/worker.rs:289`, `:315`, `:356`, `:530`, `:565`, `:618`, `:642`). Last-owner drop joins supervision at C lines 560–567; terminate escalates after 250 ms and calls kill/wait/thread joins at lines 817–835. The escalation is bounded, but the final OS wait/thread joins are not themselves a mathematical hard wall-clock guarantee. No new process architecture is indicated by this audit.
- **Deletion replay fence gap:** P writes revocation at line 138 and revokes all current matching capsules. O `observe` checks idempotency and namespace fence but never reads source revocations; S `insert_capsule` inserts status `valid` without a revocation check. A new idempotency key with the same old source can therefore write a fresh valid record. The contract permits reappearance only for a newly canonically admitted source revision; the current runtime request has no revision proof. Enforce the existing authority inside the observation transaction, including before and after encoding/race boundaries. Do not merely blacklist replay calls while ordinary observe remains open.
- **Retained provenance privacy:** S `mark_capsule_status`, lines 850–855, erases text/embedding columns but leaves `provenance`. B permits caller-supplied provenance for non-canonical-session paths at lines 998–1001. Provenance containing source content therefore remains in controlled storage after deletion. New metadata retention must include deletion/snapshot sanitization of any sensitive provenance, while preserving minimal opaque revocation/receipt evidence. Existing deletion fixtures use harmless provenance (`tests/deletion.rs:69`), so their text-removal assertions do not cover this case.
- **Snapshots already implement real privacy protection:** X restore, lines 416–540, checks the destination's revocations and builds a sanitized stage when imported sources were deleted. `tests/snapshot.rs:198` tests stale snapshot non-resurrection. Do not replace that guarantee with a snapshot format label or confuse internal reconstruction with canonical replay.

## Discriminating validation for the implementation lane

These are proposed focused tests, not executed results:

1. Build recall with the real canonical H request builder, observe a canonical Claude/Codex message, then run real `decode_recall_outcome`, scope/temporal admission and provenance validation. Require a nonempty admitted matching candidate, original source attribution and canonical content hash. Use a second truly empty namespace and require a decoded `zero_results` outcome with complete search and no fallback.
2. Feed each nested budget independently below the default; use one NCM center supporting multiple records to distinguish candidate count from top-k center count. Test per-candidate bytes, total bytes, references, warnings and extensions. Require explicit partial coverage when a bound removes results.
3. Exclude a high-scoring result separately by every exclusion class, with an admissible lower-ranked alternative present. Confirm no exclusion is silently ignored and the surviving result/coverage is truthful. Repeat after worker restart to prove durable source/observation attribution.
4. Observe old and corrected versions with retained UTC validity evidence; query current, before/after `as_of`, overlapping/non-overlapping interval and history, including exact `valid_until` boundary and superseded flags. Unknown legacy time stays unknown under the supplied policy. Privacy-deleted material stays absent even with historical/include-revoked settings.
5. Persist several observations from the same session, restart, then target exactly one candidate for feedback/correction using its stable reference while the session forget key still deletes the whole intended source group. Canonical source/session/observation identities must not collapse to numeric record IDs.
6. Observe A, export snapshot, observe B, save B's target reference, restore the older snapshot, observe C, then submit B's old target after obtaining current readiness. Require stale/unknown target and no effect on C even if its local number equals B's prior record ID. Ordinary restart and deletion rebuild must retain valid surviving references.
7. Delete a source, then redeliver its original observation with both old and fresh idempotency keys, before and after restart and stale snapshot restore. Assert zero reintroduced content/influence; an explicitly admitted new source revision is a separate positive case. Put a unique secret marker in provenance as well as text and verify deletion sanitizes both retained state and exported snapshots.
8. Cancel an in-flight **adapter** recall/handshake with a long remaining deadline and assert completion within the existing cancellation envelope, worker retirement/recovery, no successful response, and no orphan. Cancel a mutation after dispatch/commit and retain unknown/duplicate reconciliation assertions. Client-only cancellation tests do not exercise the missing adapter forwarding.
9. Compare loaded namespace commit/tick/state digest before/after recall; also open a namespace with pending deletion recovery and verify the agreed read-only/readiness boundary without accidentally admitting pre-rebuild material.
10. Run common lifecycle operations with canonical targets, settled signals, revision conflicts, item/byte limits, unknown effects and canonical-history sequence duplicates/conflicts/gaps. Assert substantive effects/counts/lineage, not just supported capability IDs or `payload.is_some()`.

Existing tests useful as foundations: provider `tests/rust_backend.rs:702` (canonical message/restart/source delete), `:788` (generation/idempotency), `:874` (durable lifecycle), `:966` (snapshot rollback), runtime `tests/engine_transactions.rs:288` (immutable recall), `:411` (recoverable feedback/correction), `tests/deletion.rs:149` (mixed-state privacy rebuild), `tests/snapshot.rs:198` (stale snapshot deletion), and `tests/worker.rs:315` (in-flight client cancellation). The purported mandatory NCM conformance fixture at `tests/rust_backend_conformance.rs:453–515` rewrites recall to `query_text`/`top_k` and checks payload presence; it does not prove the shared canonical request or host-admission path.

The node stops here. Required incomplete capabilities are canonical recall, temporal evidence/selection, exclusions and all request budgets, original host-source/observation attribution, complete common lifecycle request/result mapping, canonical-history replay, source-revision-aware anti-resurrection, and live cancellation forwarding. Current model quality/performance, real host configuration/selection, and sibling host wiring were not tested in this read-only lane.
