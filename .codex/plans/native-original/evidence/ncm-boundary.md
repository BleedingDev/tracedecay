# NCM boundary evidence

Audit point: `571daf3a9612e5247443e4da3a107b542686c1ef`. This is a read-only boundary report; no tests or model runs were performed.

## Short answer

Native restoration does not require an NCM algorithm, encoder, learning, namespace, store, worker, or lifecycle change. NCM is already an independently configured provider with the reserved identity `ncm`, an exact-scope-derived opaque namespace, a shared worker owner, and its own readiness and generation rules.

The only shared-profile dependency is compatibility admission. The NCM descriptor advertises `memory.advisory_common.v1` and its required operation capabilities, while injected active registrations currently require that profile before and after fabric registration. If the common profile is split or relaxed to accommodate the original Native provider, preserve an explicit NCM profile requirement (or a NCM-specific replacement) in the registry. Do not make the active gate globally permissive and do not infer compatibility from the provider name.

## Observable acceptance checklist

- With Native disabled and NCM enabled/selected, project composition registers exactly provider `ncm`; the active registration retains its explicit profile requirement, `exact_coding_scope` binding, existing lifecycle owner, and adapter-attested scope mount. No Native registration is needed.
- With Native enabled as an observer or disabled, NCM’s active reply identity, exact-scope binding, and worker owner remain unchanged. An NCM observer-only registration cannot answer active recall.
- If the common profile is relaxed for Native, an active NCM descriptor missing its own declared profile/required capabilities is rejected before provider work, while a complete NCM descriptor remains admissible. The check is based on the explicit profile declaration and descriptor identity.
- Disabling NCM or building without the NCM backend feature creates no NCM adapter, worker process, journal, namespace store, or route. Enabling NCM still uses one owner per admitted profile/binary/state-root binding.
- For one exact scope, re-handshake after a committed mutation admits the returned generation; a call with retired readiness fails, and the same namespace/source deletion identity is preserved across provider restart. Native profile changes do not alter these observations.
- The previously observed Codex recall journey was unstable (2/4 and later 4/4). This report does not explain or fix that result. Final integration acceptance must rerun the journey repeatedly and record the aggregate outcome instead of treating one passing run as proof.

## Bounded Luna Max implementation assignment proposal

**Goal:** Preserve real NCM behavior while allowing the restored Native descriptor to use an explicitly different or relaxed profile.

**Prerequisites:** The contract lane publishes the final profile IDs, required capability sets, canonical field compatibility, and exact-scope compatibility rule; the Native lane publishes its descriptor and registration shape.

**Files:** Registry compatibility seam and focused registry tests first. Then, only if required by the published contract, NCM `capability_ids`/common projection and `ncm_observer.rs` registration construction/tests. Do not edit NCM core/runtime/model/store/worker.

**Steps:** Add the explicit per-registration profile requirement; set it for NCM; preserve NCM’s declared scope binding and lifecycle owner; update only compile-time/profile mapping seams for a renamed profile; exercise disabled/observer/active selection, incomplete-profile rejection, exact-scope namespace stability, readiness retirement, and restart/source deletion.

**Verification:** Run the focused registry and NCM boundary suites, then the repeated host NCM/Native journeys with isolated state. Report the aggregate Codex outcome and any remaining effect-unknown or readiness failures.

**Forbidden shortcuts:** Do not remove the common/profile gate globally, infer compatibility from `provider_id == "ncm"`, substitute Native output or fallback ranking, alter NCM scoring/model/projections/learning schedule, broaden namespace identity, or claim the unstable recall journey is fixed from one run.

**Stop condition:** Stop after the published profile contract is admitted by the registry and the existing NCM boundary behavior remains observable. If the profile contract is still unsettled, leave NCM source untouched and return the exact missing contract decision.
