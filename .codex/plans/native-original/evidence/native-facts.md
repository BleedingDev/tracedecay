# Native fact behavior evidence

## Revision and answer

The comparison uses current head `571daf3a9612e5247443e4da3a107b542686c1ef` and the exact upstream-authored second parent `b3b43410e47115056f2066449aafa1822bbb6049`. The Native fact implementation under `crates/tracedecay-session-memory/**` is unchanged between those revisions; the only relevant change in `crates/tracedecay-store-runtime/src/retained_memory.rs` is making `memory_application` visible to the adapter. The pinned `b3b` tree is therefore the correct original fact baseline for this report.

Original Native facts are canonical, owner-bound, SQLite-backed fact/event records. Direct retained execution opens the authority-selected project or profile database, constructs `MemoryApplication<DatabaseFactStore>`, and sends add, read/search, feedback, update, removal, supersession, status, and automation/curation work through that application. A canonical write is an append-only assertion/event commit that updates the current projection, records an idempotent operation receipt, purges superseded payloads where required, and schedules the verified project-memory graph publication. Search computes the original fixed-point score and deterministic order. The pure search use case does not write, but the production direct `FactStoreSearch` entry point follows a nonempty search with `track_explicit_search`, which records retrieval telemetry and returns refreshed projections. Probe, related, reason, contradiction, get, and list use the read lane and do not perform that retrieval write.

The current provider port is a different state machine. `FactPromotion` verifies a fact that the host says is already canonically settled; it does not perform a new fact write. `StagedSession` writes only provider-local staged rows. Normal provider recall calls the original search/probe/related/reason use cases for current project facts, then merges those facts with staged rows under an adapter-defined scorer and reports partial lineage. Common advisory recall deliberately constructs an empty canonical page and reads only staged rows. Provider recall does not call the original retrieval command. Feedback, correction, deletion, maintenance, snapshot, restore, replay, and inspection are dispatched to the staged store and produce provider-local generations/receipts. These are durable staged effects, but they are not the original Native fact effects. Native Mod is excluded from the target behavior: the staged implementation is a substitute to retire from the Native path, not a second Native or hidden advisory lane. Its use currently suppresses canonical retrieval, trust/history, lineage, correction/deletion, curation/maintenance, ownership, and persistence behavior whenever the provider route is treated as Native.

The direct canonical route still exists. Current MCP retained handlers send profile-scoped fact operations through `DirectRetainedMemoryPortV1::profile`, and the mounted project retained port sends project operations through `DirectRetainedMemoryPortV1::project`. That route is evidence that the original backend is present; it does not make the provider adapter equivalent to it.

## Side-effect inventory

The original write/read boundaries are:

- **Canonical add or promotion:** sanitize and validate owner/provenance, classify duplicate/conflict, append the initial assertion and `AssertionRecorded` lineage, publish the current projection, write the idempotency receipt, and publish graph state after a committed result.
- **Canonical read:** list/get/status/inspection/history/lineage/anchor and semantic probe/related/reason are authority reads. They validate cancellation/deadline through `FactReadControl` but do not increment retrieval telemetry.
- **Explicit Search:** query and score from a read snapshot first. The direct retained runtime then records a retrieval command for all returned hits when the page is nonempty, increments the retrieval/access counters and timestamps, persists an idempotent retrieval receipt, reloads hit projections, and renders the result. This is the only production caller found for `track_explicit_search` in `b3b`.
- **Feedback:** append trust and feedback lineage, update trust/counters/history/finding, and return a canonical receipt. Trust changes affect subsequent search scores.
- **Update/remove/supersede/curation:** append the appropriate correction, deleted-access, or curation event with CAS and receipts; update/tombstone/purge projections as the original transaction requires.
- **Privacy/maintenance:** rescan and purge through the canonical authority, including quarantine by curation removal. It is not staged-row retention maintenance.

The current provider preserves only some canonical read semantics on its normal current path. It suppresses the explicit-search write, mixes canonical hits with staged rows using a new score/order, presents an empty canonical page for common advisory recall, and sends all lifecycle calls to staged state. A provider-local staged row can be durable and correctly idempotent while still having no canonical fact effect.

## Observable acceptance checklist

- Seed an isolated project and an isolated profile through the direct canonical add path. When a Native provider operation claims a new fact, it must use an existing canonical add route and leave a canonical `memory_v2` projection, assertion/event lineage, provenance, and operation receipt visible after closing and reopening the database. Same logical retry is the original duplicate/replay outcome; changed payload is a typed conflict. A `FactPromotion` verification or staged row alone never satisfies this check.
- Run direct and provider current `FactStoreSearch` against the same canonical facts. Returned fact IDs, canonical contents, `why`, graph coverage/degradation, score components, fixed-point combined scores, tie ordering, cursor behavior, current validity, and source references agree. Staged candidates do not appear in the Native fact result; the staged merge must be retired from that path.
- After a nonempty explicit Search, inspect canonical projections and retrieval receipts. Every returned fact has the original retrieval/access/timestamp update exactly once for the operation, and the refreshed projection is returned. Repeat the same operation identity and verify idempotent replay. Run Probe, Related, Reason, Contradict, Get, and List and verify their retrieval counters and receipts do not change.
- Record helpful and unhelpful feedback through the provider. Canonical trust changes by the original action deltas with clamping; `TrustChanged` lineage, feedback history, helpful/unhelpful counters, finding, refreshed projection, and operation receipt are present. A provider-local feedback generation is insufficient.
- Apply an update/correction and verify the canonical correction assertion/event, CAS behavior, sanitized payload, current projection, trust/access events, and receipt. Remove a fact and verify the canonical Deleted projection, derivative tombstones, purge behavior, and original not-found/already-removed/replay outcomes. Supersede or merge facts and verify the canonical curation relation and successor/winner/loser effects.
- Run Native maintenance/privacy/curation behavior against canonical facts. The sanitizer revision, purge counts/cursors, quarantine/removal effects, curation effects, graph publication, and receipts survive restart. A staged retention or deletion fence is not evidence of this behavior.
- Exercise project and profile owners from their admitted public routes. Each operation opens the correct authority; an incorrect project/selector or exact-scope mismatch fails closed without reading or mutating another owner. Repository/worktree/branch/session fields constrain admission only and do not split a project fact owner.
- Exercise every temporal/history operation promised by the provider contract. An original as-of/lineage/history result is returned through its corresponding API, or the interface reports an explicit typed unsupported result where no original direct operation exists. A current projection is never labelled historical, and an unsupported request never returns a successful empty canonical page.
- Close and reopen the canonical store and provider composition. Facts, lineage, trust, retrieval counters/receipts, curation and privacy receipts remain in the canonical authority and produce the same direct/provider semantic results. Cancellation, deadline, invalid owner, stale CAS, and response-budget failures have the documented no-effect or effect-unknown terminal without a fabricated canonical success.

## Unknowns and conflicting evidence

1. ADR-0010 was accepted after the pinned fact implementation and explicitly says provider recall must be read-only, generic lifecycle operations are unsupported, and provider feedback must not mutate Native trust. That conflicts with the latest requirement to restore complete original Native behavior. This report follows the latest requirement; updating or superseding the ADR is documentation follow-up, not an implementation prerequisite.
2. `native.fact_promoted.v1` is described by the current observation contract as a source event that has already passed Native validation and durable promotion. It is therefore unknown whether the desired provider call is only post-settlement verification or whether a separate provider-facing explicit promotion command is required. The implementation must not blindly commit the same fact twice.
3. The original `b3b` retained operation set has typed fact add/search/probe/related/reason/contradict/get/list/update/remove/supersede/feedback/status, while the current provider adds generic maintenance, inspection, correction, source deletion, snapshot, restore, and replay operations. Use the existing typed Native routes wherever the request corresponds to one. If a promised generic operation has no exact route, record the concrete request/result gap for root; do not infer that every internal helper needs a new provider capability.
4. The underlying original fact store exposes current/as-of/lineage/response/anchor APIs, but the original retained project-memory search surface is current-projection search. The provider's explicit rejection of non-current modes and unavailable full lineage are reductions that need an intentional typed boundary. A generic automatic/context query must map to its corresponding original read-only objective; it is not automatically an explicit Search.
5. The project-mounted adapter does not establish a profile Native provider route even though the original direct port supports `FactOwnerV1::Profile`. Treat this as a composition gap to resolve through the existing profile route or escalate concretely to root; exact-scope fields cannot be used to infer a new profile/project owner.
6. Existing staged rows carry settled observation provenance but are not canonical fact commands. No source evidence authorizes automatic migration or promotion of those rows into `memory_v2`; the Native path must not auto-promote or retain them as a Native supplement. A separate explicit Native promotion command would need its own canonical receipt.

## Proposed bounded Luna Max implementation assignment

**Goal.** Make the Native provider route an owner-bound thin adapter over the original `b3b` Native fact application. Direct and provider Native operations must have the same canonical state changes, scores, retrieval boundary, receipts, ownership, and restart behavior. Retire the staged substitute from Native composition; it is not a Native advisory supplement.

**Starting boundary.** Use the current requirement as authority and the existing public Native APIs as the integration surface. Original fact implementation files remain unchanged. If a required operation is not reachable through those APIs, isolate the exact missing boundary for root and use an unprotected composition refactor or a separately decided contract change; do not add wrappers or algorithms inside the original fact files.

**Files.** The adapter lane owns `crates/tracedecay/src/daemon/retained_owner/native_provider.rs` and, if needed, one narrow adjacent bridge module. The existing canonical fact files are read-only integration dependencies. Any contract or composition change must be limited to a concrete missing provider boundary; the adapter does not modify original fact files or the staged implementation to emulate them.

**Steps.**

1. Bind each provider call to the exact `FactOwnerV1` and authority-selected `Database`/`ProjectFactStore`; reject owner or target mismatches before any canonical read/write.
2. Map canonical fact add/explicit promotion, current reads, search objectives, feedback, update/correction, removal/source deletion, supersession/merge, privacy/maintenance, and automatic-fact operations to the existing typed Native routes and `MemoryApplication` methods. Preserve each method's sanitizer, CAS, idempotency, transaction, graph publication, and receipt behavior. Use a thin adapter mapping; do not copy internal algorithms or add wrappers in the original files.
3. For provider explicit Search, reuse the existing `DirectRetainedMemoryPortV1` project/profile route so the original query/filter/objective/limit/cursor, scoring path, and nonempty-page retrieval tracking remain intact. Map generic automatic/context queries to the corresponding original read-only objective and do not turn them into explicit Search. Return canonical score/why/provenance/validity fields without adapter re-ranking. Remove staged rows from this Native fact result and retire the current staged merge/empty-page substitute.
4. Map canonical feedback and lifecycle outcomes to their real Native receipts and terminal states. If a generic provider request cannot express an original operation, stop at that concrete boundary and escalate to root or make the required unprotected composition/contract change; never dispatch `StagedObservationStore::control` or return a staged success as Native. Do not claim that every original internal helper requires a generic provider capability.
5. Preserve project/profile public routing and ensure provider exact-scope metadata remains admission/routing data. Do not narrow canonical project facts to a checkout or session, and do not infer profile ownership from a path or envelope field.
6. Run the behavioral checks in the acceptance list in isolated stores, including direct-versus-provider comparison, retrieval delta/no-delta cases, mutations, owner mismatch, restart, cancellation/deadline, and effect-unknown recovery. Update capability declarations only after those behaviors are real.

**Forbidden shortcuts.** Do not copy the fact algorithms into the adapter, retain the staged lexical/recency scorer or staged rows for Native facts, build an empty canonical page, suppress the explicit Search retrieval write, map generic automatic/context queries to explicit Search without evidence, route canonical feedback/correction/deletion/maintenance to staged control, invent profile/checkout ownership, auto-promote staged rows, fabricate lineage/receipts, edit the original fact files, or use ADR-0010's historical unsupported/read-only decision to avoid implementing the latest requirement.

**Stop condition.** Stop with a concrete interface blocker and leave the adapter unchanged if any original operation lacks a typed request/receipt mapping, authority owner, or observable state transition. The assignment is complete only when every promised Native capability passes the direct/provider behavioral checks and no canonical fact behavior is implemented by the staged store.
